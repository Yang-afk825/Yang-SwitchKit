## 一、定位与一条红线

### 1.1 定位

离线模式是**完整版**，在线模式是**增强包**。这条不能反过来，原因有两个：

1. 用户是学生和初入行的网工，网断、欠费、API 停服都是常态。增强包失效不该让工具变残废。
2. 这个工具的价值锚点是「离线」和「正确」（见 README 开头）。在线能力一旦成为主路径，护城河就从「核对过的命令库」变成「模型的运气」。

所以产品文案、界面默认值、启动流程，全部以离线优先。

### 1.2 红线：AI 填参数，不写命令

**任何情况下，模型输出的内容都不会被当作命令直接展示或执行。**

```
自然语言  ──AI──▶  {scenario: "vlan_port", params: {...}}  ──▶  registry + vendors  ──▶  命令
                          ↑ 只到这里                                    ↑ 命令只有这一个来源
```

理由，按重要性排：

1. **正确性不可转嫁。** 现有 116 组模板、170 条详解、`verify.FIXED` 里那 7 条修正（ACL 编号区间、`mirror` 漏 `ing`、锐捷默认关着 ssh-server、时区四家写法不同、接口名被空格劈断），是拿官方手册逐条核出来的。模型在这些细节上错得比人更自信，而且错法随机，回归测试抓不住。
2. **可审计。** 参数是有限的、可枚举的、可校验的。命令不是。
3. **可回退。** 参数回填到表单后用户看得见、改得动，跟现有「填参数 → 生成 → 核对」的心智模型一致。如果 AI 直接吐一段脚本，用户就失去了中间那个可以纠正的位置。
4. **降级无损。** AI 挂了只是少了一个填表单的快捷键，生成能力一点不减。

查错功能同理：**只输出问题清单，不改用户的命令**。

```

**硬边界：**

| 模块 | 允许 | 禁止 |
|---|---|---|
| `provider.py` | 发 HTTP、解析响应、流式回调 | 拼提示词、碰 Tkinter、碰 registry |
| `intent.py` | 组装提示词、解析 JSON、校验参数 | 生成命令字符串 |
| `advise.py` | 组提示词、清洗模型返回 | 修改用户输入、写回报告区 |
| `rules.py` | 纯数据 + 纯函数 | 任何 IO |
| `ui/ai_page.py` | 画控件、起线程、收结果 | 自己发 HTTP |

**跟 `audit.py` 的分工**（这条最容易搞混）：

| | audit.py | ai/rules.py |
|---|---|---|
| 看什么 | **安全** | **语法与结构** |
| 典型发现 | SNMP 用 public、VLAN1 当管理口、没配 NTP、空闲端口没关 | 命令跑错视图、基础 ACL 带协议字段、端口编号不符惯例、拼写错误 |
| 回答 | 这台设备安不安全 | 这段配置能不能跑 |
| 视角 | 等保测评、项目验收 | 下发前的最后一道自检 |

## 三、provider 层：一个实现打通所有供应商

### 3.1 为什么只写一个

DeepSeek、通义、智谱、月之暗面、OpenAI、vLLM、ollama，全都提供 `/v1/chat/completions`。
写一个 `OpenAICompatProvider` + 可配置 `base_url`，覆盖全部，维护成本最低。
换供应商只需要用户改一个地址，不用改代码、不用发版。

### 3.2 请求形态

只用标准库，`urllib.request` + `json`。

```
POST {base_url}/chat/completions
Authorization: Bearer {key}
Content-Type: application/json

{
  "model": "...",
  "messages": [{"role": "system"|"user", "content": "..."}],
  "temperature": 0.1,
  "max_tokens": 1200,
  "stream": true,
  "response_format": {"type": "json_object"}
}
```

三个选择要说明：

- **`temperature: 0.1`** —— 这是参数抽取任务，不是创作。温度高只会让它在端口号上瞎编。
- **`response_format: json_object`** —— 支持就带上，不支持的服务端会忽略，所以要能容忍缺失。解析端仍然要做「从文本里抠 JSON」的兜底（模型常在 JSON 前后加 ```json 围栏或一句解释）。
- **`stream: true`** —— 关掉的话，2-8 秒内界面什么都不动，用户会以为卡死。流式让首字 1 秒内出现。但**流式只用于展示，最终仍以完整响应的 JSON 为准**，不做增量解析。

### 3.3 SSE 解析

`urllib` 的响应对象是可迭代的字节流，按行读即可，不需要第三方库：

```
for raw in resp:                     # 每次一行
    line = raw.decode("utf-8").strip()
    if not line.startswith("data:"):
        continue
    payload = line[5:].strip()
    if payload == "[DONE]":
        break
    delta = json.loads(payload)["choices"][0].get("delta", {})
    text = delta.get("content") or ""
    if text:
        on_chunk(text)               # 回调给 UI，UI 自己决定要不要实时显示
```

注意三件事：`data:` 后面可能有也可能没有空格；`delta` 里可能只有 `role` 没有 `content`；`finish_reason` 出现后可能还有一行 `[DONE]`。

### 3.4 错误映射

不把异常往上抛成一坨 traceback，统一转成 `AIError(code, message)`：

| 情况 | code | 界面文案 |
|---|---|---|
| 未配置 key | `not_configured` | 还没配置接口地址和密钥，当前是纯离线模式 |
| DNS / 连不上 | `network` | 连不上服务器，检查网络或接口地址 |
| 超时（默认 15s） | `timeout` | 服务器没在 15 秒内响应，可以重试 |
| 401 / 403 | `auth` | 密钥无效或已失效，去设置里重新填 |
| 429 | `rate_limit` | 请求太频繁或余额不足，稍后再试 |
| 400（模型名错） | `bad_request` | 服务端拒绝了请求，多半是模型名写错了 |
| 5xx | `server` | 服务端出错，不是你的问题，稍后重试 |
| 返回不是 JSON | `bad_format` | 模型没按要求的格式返回，已保留原文 |

**不自动重试。** 用户是自费的，429 和超时自动重试三遍等于替他烧钱。给一个「重试」按钮，让他自己决定。

## 四、intent：自然语言 → 参数

### 4.1 两段式上下文

29 个场景的参数全量塞进去约 6-8k token，每问一句都烧一遍不划算。分两轮：

**第一轮（路由）** —— 只给场景清单：

```
key | 名称 | 一句话摘要 | 参数名列表
vlan_port | VLAN 创建与端口划分 | 批量建 VLAN，端口配成 Access 或 Trunk | vlans, vlan_names, port_type, ports, allowed, pvid
lag | 链路聚合（LACP） | ... | group, mode, ports, ...
...
```

约 2.5k token。输出只要 `{"scenario": "...", "confidence": 0.0-1.0}`。

**第二轮（抽参）** —— 只给选中场景的完整 schema：

```
vlan_port 参数：
  vlans       VLAN 列表   text   必填  例 10,20,30   逗号分隔，支持区间
  port_type   端口模式    choice 必填  可选 access|trunk（显示为"Access（接终端）"）
  ports       端口        text   必填  例 1/0/1-8     支持 1/0/1-8、1/0/1-1/0/8
  ...
当前已填：{"vlans": "", "ports": ""}
厂商：h3c（接口从 1/0/1 起）
```

约 800 token。输出完整参数 JSON。

`confidence < 0.6` 时不自动填，改成让用户在候选中选。宁可多一步，不要填错一屏。

### 4.2 输出契约

```json
{
  "scenario": "vlan_port",
  "confidence": 0.86,
  "params": {
    "vlans": "10,20,30",
    "port_type": "access",
    "ports": "1/0/1-8"
  },
  "missing": ["allowed"],
  "question": "这 8 个口是接终端，还是要跟另一台交换机互联做 Trunk？",
  "note": "按 Access 口处理；如果要做互联，端口模式和放通 VLAN 需要改。"
}
```

规则：

- `params` 的 key 必须来自该场景的 `Param.key`，多余的丢弃并记警告
- 值一律是**字符串**（原因见 4.3）
- 拿不准的参数**不填**，放进 `missing`，用 `question` 反问，而不是猜一个默认值
- `note` 给用户看，可空

### 4.3 从 registry 自动生成 schema

新增 `registry.export_schema(scenario) -> dict`，从 `Param` 直接翻译，不手写第二份：

| `Kind` | JSON Schema |
|---|---|
| `TEXT` / `AREA` | `{"type": "string"}` |
| `NUM` | `{"type": "string", "pattern": "^-?\\d+$"}` |
| `CHOICE` | `{"type": "string", "enum": [全部 value]}` |
| `BOOL` | `{"type": "string", "enum": ["1", ""]}` |

**全用 `string`，不用 `integer`。** 这是个真实的坑：`window._collect()` 返回的每个值都是 `str`，`project.load()` 也强制 `str(v)`。schema 里写成 `integer` 会让模型输出数字，回填时再转，中间多一次出错机会，而现有校验（`vendors/base.parse_vlans`、`ports.expand`）本来就是按字符串设计的。

`CHOICE` 的 `enum` 取 `choices` 里的 **value**（`access` / `trunk`），不是界面标签（`Access（接终端）`）。标签在 `window.choice_maps` 里做映射，AI 层不碰它。

`help` 与 `example` 拼进 `description`，模型对「支持 1/0/1-8、1/0/1-1/0/8」这种提示的遵循度明显高于纯字段名。

### 4.4 回填流程

关键点：**生成逻辑一行都不改**。现有链路已经够用。

```
intent.resolve()  →  诊断 JSON
        ↓
ai_page 校验：scenario 存在？params key 合法？厂商支持该场景（vendors.supports）？
        ↓
写 self.store[(vendor_key, scenario_key)] = 合并后的参数
        ↓
self._restore_fields()          ← 界面控件跟着变（现有方法，直接复用）
        ↓
self._generate(scenario_key)    ← 现有方法，返回 bool，内部已经处理 ValueError / 不支持 / 异常
        ↓
高亮：把这次被改动的参数控件背景标一下，3 秒后恢复
```

`store` 是现有结构：`(厂商, 场景) -> {参数: 值}`。AI 只是往这个 dict 里写，跟用户在表单里手填的效果完全一样。所以：

- 切厂商不丢值 —— 现有行为，自动继承
- `Ctrl+S` 存方案能存下来 —— 现有行为，自动继承
- 生成失败照常红字 —— `_generate` 里已有 `except ValueError` 分支

**高亮必须做。** 否则用户看见表单自己变了、脚本自己出来了，会分不清哪几个值是他填的、哪几个是 AI 填的。这是这个功能最容易让人不信任的地方。

### 4.5 反问而不是猜

`missing` 非空时，界面显示 `question`，并提供两个选项：「按默认值补全」和「我来填」。
不自动用 `Param.default` 补 —— 默认值在演示里都挺好看（VLAN 10,20,30），直接下发到现网就是事故。

## 五、体检的后两层：语法校对与语义补充

「配置体检」页在 3.0 里只有一层安全体检。3.1 加了后两层，三层递进：

```
用户在「配置体检」页粘一段 current-configuration
   ↓
① audit.analyze()          安全体检   ← 永远执行，0 网络，等保视角
   ↓  风险清单 + 健康分
② ai/rules.check()         语法校对   ← 永远执行，0 网络，毫秒级
   ↓  findings + 未识别行（difflib 给近似写法）
③ ai/advise.review()       语义补充   ← 只在配了 key 且用户勾选时执行
   ↓  配置冲突 / 缺配套命令 / 策略顺序
右侧报告区依次渲染三段
```

①②不联网也跑。这是「断网时还剩什么」的答案：**最常见的错误基本都在①②里**。

原来的设计是把查错做成独立页签，3.1 合入 3.0 时改掉了——体检页本来就有
粘贴区、报告区和复制按钮，再开一个查错入口只会让人不知道往哪粘。
详见附录 B。

### 5.1 为什么规则层不跟 audit 合并

两层看起来都是「粘配置 → 出问题」，但判据来源完全不同：

* `audit.py` 的规则是**安全基线**——SNMP 团体名、VLAN1 管理、NTP、空闲端口。
  这些是「应该配但没配」，属于建议性质，需要判断配置完整性才敢下结论。
* `rules.py` 的规则是**语法事实**——命令在哪个视图执行、ACL 类型的编号区间、
  关键字拼写。这些是「配了但配错」，对错是确定的，不依赖上下文完整性。

混在一起会让「不可误报」这条原则失效：语法错误必须在任何情况下都报，
而安全建议在配置不完整时必须降级。两套阈值放在一个函数里会互相干扰。

### 5.2 五类规则

规则表写成纯数据，放在 `rules.py`，每类一个函数。这样可以单独跑 `tools/ai_test.py` 验证。

**R1 厂商语法错配（error，阻断）**

拿四家的特征 token 给输入"验明正身"，跟用户当前选的厂商对不上就报。

| 特征 token | 语法族 |
|---|---|
| `port link-type` / `port trunk permit` / `port access vlan` | H3C |
| `port link-type` / `port trunk allow-pass` / `port default vlan` | 华为 |
| `switchport mode` / `switchport trunk allowed vlan` | 思科 / 锐捷 |

`port link-type` 是 H3C 和华为共有的，要靠 `permit`（H3C）/ `allow-pass`（华为）、`access vlan`（H3C）/ `default vlan`（华为）二次区分。这正好是 README 里点名的跨厂商陷阱。

**R2 视图错位（error，阻断）**

维护一张 `{命令前缀: {合法视图}}` 的表，扫描时跟踪视图栈：

```
system-view / configure terminal   → 系统视图
interface X                        → 接口视图（入栈）
quit / exit / #                    → 出栈
```

典型错误：`port link-type trunk` 出现在系统视图（用户漏了 `interface`），
或者 `stp global enable` 出现在接口视图里。

视图栈要用栈而不是单个变量——嵌套两层的情况真实存在（`interface` 下再进 `port-group`）。

**R3 已知陷阱（error / warn）**

直接把 `verify.FIXED` 那 7 条翻译成可执行判断。这是全项目最值钱的资产，值得逐条硬编码：

| 陷阱 | 判据 | 级别 |
|---|---|---|
| 基础 ACL 带协议字段 | 编号 < 2000（H3C/华为）或 1-99/1300-1999（思科/锐捷）的 ACL 块内出现 `ip`/`tcp`/`udp` 或目的地址 | error |
| 华为 VLAN 镜像关键字错 | 出现 `mirror to observe-port`（缺 `ing`）或 `mirroring ... both` | error |
| 锐捷未开 SSH 服务端 | 有 `ssh` / `line vty` 相关配置但全文无 `enable service ssh-server` | error |
| 锐捷多余命令 | 出现 `no service telnet`（RGOS 无此含义） | warn |
| 时区带符号冒号 | `clock timezone` 后出现 `UTC+08:00` / `+08:00` 形式 | error |
| 接口名被空格劈断 | 出现孤立的 `silent-interface Vlan-interface` 或 `silent-interface 10` | error |
| 堆叠未提示中断 | 出现 `irf` / `stack` / `vsu` / `switch virtual domain` 但未在维护窗口 | info |

**R4 端口编号惯例（warn）**

| 厂商 | 起始 | 检测 |
|---|---|---|
| H3C | `1/0/1` 起，三段 | 出现 `0/0/1` → 提示"华为的编号习惯，H3C 一般从 1/0/1 起" |
| 华为 | `0/0/1` 起，三段 | 出现 `1/0/1` → 提示（可能是堆叠第二台，不算错，只 warn） |
| 思科 / 锐捷 | 单机两段 | 出现三段 → 提示"仅在堆叠/模块化机型两段不适用" |

只 warn 不 error —— 堆叠场景下这些"异常"是正常的。这跟 `convert.py` 的处理原则一致：**摆出来让人核，不偷偷改**。

**R5 未识别语法（info，最有用的那条）**

```
doc = explain.match(vendor_key, line)
if doc is None and not 注释 and not 空行:
    cand = difflib.get_close_matches(line, 该厂商全部 syntax, n=1, cutoff=0.6)
    → "这条命令不在已知语法库内。最接近的是：port link-type trunk"
```

成本几乎为零（现有 170 条正则 + 标准库 `difflib`），但能抓住拼写错误、版本差异、
以及"从网上抄了一段别的厂商的命令"这三种高频情况。

它同时也是个**覆盖率探针**：如果真实用户粘的配置大量命中 R5，
说明 `explain.CATALOG` 该补概念了。这个统计数据值得记进本地日志。

### 5.3 输出契约

```json
{
  "vendor": "h3c",
  "line_count": 42,
  "findings": [
    {
      "line": 12,
      "text": "port link-type trunk",
      "level": "error",
      "rule": "R2-view",
      "message": "这条命令必须在接口视图下执行，当前位置是系统视图",
      "evidence": "第 8 行 system-view 之后没有 interface 语句",
      "fix": "先 interface GigabitEthernet1/0/1 进入接口，再执行本命令"
    }
  ],
  "unmatched": [{"line": 27, "text": "port trunk permit vlan 10 20", "suggest": "..."}],
  "summary": {"error": 1, "warn": 2, "info": 3}
}
```

每条必须带 `evidence` —— 指到具体行号或具体缺失的命令。
没有依据的判断不如不给，网工不会因为一句"这里可能有问题"就去改现网配置。

### 5.4 在线语义层补什么

离线层抓的是「拼写和位置」，在线层补的是「意图和关系」：

- 两段配置互相冲突（VLAN 放通了但 PVID 又改回去了）
- 缺配套命令（配了 DHCP 池但没在接口上 `dhcp select`）
- 策略顺序（ACL 的 deny 写在 permit 前面，后面的全废）
- 报错信息解读（用户直接粘 `% Unrecognized command found at '^' position`）

提示词里必须带三样东西：当前厂商、粘贴的原文、离线层已发现的问题。
让模型**只补充离线层没覆盖的部分**，避免它把已知问题重复讲一遍、或者推翻离线层的结论。

## 六、界面落点

### 6.1 两个入口，都不动现有布局

```
一键生成配置命令 | 设备命令详解 | AI 助手 | 配置体检 | 配置对比 | 故障排查 | 核验说明 | 使用说明

**为什么 AI 助手单独开一页**：主页面是「左脚本 + 右参数」的两栏满负荷布局，

**为什么查错不单独开页**：3.0 的「配置体检」已经是左边粘、右边报告。
再开一个查错入口，用户会不知道该往哪粘。所以做成体检页的第三层，
共用同一个粘贴区和报告区。

## 七、线程模型（最容易踩的坑）

Tkinter 是单线程。现有代码里所有操作都是同步的，用户点按钮 → 立刻有结果。
一旦加网络请求，**直接在主线程调 `urlopen` 会让窗口假死 2-8 秒**，
Windows 上还会被标记为「未响应」，用户以为程序崩了。

### 7.1 固定模式：worker 只进队列，主线程轮询

```
主线程                                    worker 线程
  │
  ├─ 点「解析」
  ├─ 禁用按钮 + 状态行「正在请求…」
  ├─ threading.Thread(daemon=True).start() ──▶ urlopen（可能在跑 15s）
  ├─ self.after(100, self._poll)              │
  │      └─ 每 100ms 看一次 queue 空不空       │
  │                                           │
  │◀──────────── queue.put(("ok", payload)) ──┘
  ├─ 拿到结果 → 回填 → _generate()
  └─ 恢复按钮
```

三条铁律：

1. **worker 里绝不碰任何 tkinter 控件、变量、甚至 `self.store`。** 只做纯计算和 IO，结果放 `queue.Queue`。
2. **不用 `self.after` 直接从 worker 调。** CPython 里它多数时候能用，但它不是一个有保证的线程安全入口，跨解释器版本行为不同。用队列轮询，行为确定。
3. **超时和异常也必须走队列**。否则按钮永远停用、状态行永远停在「正在请求…」——这是这类代码最常见的事故。

`daemon=True` 是必须的：用户关窗口时不能让一个还在等的 HTTP 请求拖着进程不退出。

### 7.2 超时怎么拆

`urlopen(timeout=15)` 只管到「连接 + 首字节」。流式响应一旦开始，
后面每个 chunk 之间的停顿不受这个 timeout 管。所以要再加一个**整体看门狗**：

```
deadline = time.monotonic() + 45      # 整体上限，比单次超时长
for raw in resp:
    if time.monotonic() > deadline:
        raise AIError("timeout", "整体响应超过 45 秒，已中断")
```

15 秒是"多久没反应算失败"，45 秒是"一次对话最多等多久"。两个数字分开配。

## 八、配置与安全

### 8.1 密钥用 DPAPI 加密，不存明文

Windows 自带 `crypt32.dll` 的 `CryptProtectData` / `CryptUnprotectData`，
用 `ctypes` 调即可，标准库范围内。

```python
# 加密后只有「本机 + 当前 Windows 用户」能解开
blob = dpapi.protect(key.encode("utf-8"))
```

配置文件：`%APPDATA%\YangSwitchKit\ai.json`

```json
{
  "format": "yang-switchkit-ai",
  "format_version": 1,
  "base_url": "https://api.deepseek.com/v1",
  "model": "deepseek-chat",
  "key_protected": "base64...",
  "timeout": 15,
  "redact": true,
  "stream": true
}
```

换机器或换 Windows 用户后解不开——这是**预期行为**，提示「密钥无法解密，请重新填写」，不报错崩溃。

### 8.2 绝不进方案文件

`project.Project` 的字段里**不能出现任何 AI 配置**。

原因很具体：方案 `.json` 是要进 git、要发给同事、要作为交付物交接的（README 明写了这一点）。
一旦 base_url 和密钥混进去，就是一次凭据泄露。这条要在 `project.py` 的模块说明里加一句注释钉死。

### 8.3 脱敏

在线查错时，粘贴的配置里有内网 IP、ACL、明文密码。默认开脱敏，发送前替换：

| 类型 | 正则 | 替换成 |
|---|---|---|
| IPv4 | `\b\d{1,3}(\.\d{1,3}){3}\b` | `x.x.x.x` |
| MAC | `\b[0-9a-f]{4}[.-][0-9a-f]{4}[.-][0-9a-f]{4}\b` | `xxxx.xxxx.xxxx` |
| 密码 | `(?i)(password\|secret\|cipher\|key)\s+\S+` | `\1 ******` |
| 主机名 / 域名 | `(?i)(sysname\|hostname)\s+\S+` | `\1 SW` |

顶部固定显示一行：**「已脱敏 12 处，原文只在本机」**。让用户看见发生了什么，而不是偷偷改。

关掉脱敏是个显式勾选，勾的时候弹一次确认。

## 十、里程碑与验收

| 里程碑 | 内容 | 产出 |
|---|---|---|
| M1 | `provider.py` + `config.py` + 设置弹窗 + 测试连接 | 能发通一条请求，key 能存能解 |
| M2 | `rules.py` + `diagnose.py` 离线层 + `tools/ai_test.py` | 断网可查错，20 条固定样本可回归 |
| M3 | `schema.py` + `intent.py` 两段式 + 回填高亮 | 一句话能填满表单并生成 |
| M4 | 在线语义层 + 脱敏 + 流式展示 | 完整双模 |
| M5 | 降级打磨 + README / ARCHITECTURE / CHANGELOG 更新 | 可发版 |

### 验收标准（可执行，不是感觉）

1. **离线完整性**：拔网线、删 `ai.json`，29 个场景全部能生成、四个页签全部可用。
2. **不假死**：worker 里 `sleep(20)`，窗口仍可拖动、可切页、可滚动。
3. **不写命令**：grep 全项目，`scg/ai/` 里不允许出现任何厂商命令关键字（`system-view`、`port link-type` 等）。这条可以用 `tools/ai_test.py` 做静态检查。
4. **规则召回**：`verify.FIXED` 那 7 条陷阱各造一个样本，离线层必须全部命中。
5. **不泄露**：方案 `.json` 里 grep 不到 `key` / `base_url` / `api`。
6. **启动路径干净**：`scg/ai/` 不在 `main.py → window → ai_page` 的顶层导入链上，
   只有 AI 页画完之后（`after(200)`）才加载。删掉整个 `scg/ai/` 目录，
   主程序仍能启动，只是 AI 页显示不可用。

第 3 条和第 6 条是最重要的两条——它们把「AI 不写命令」和「离线优先」从约定变成了机器可查的约束。

## 十一、明确不做的事

| 不做 | 原因 |
|---|---|
| 设备直连下发（SSH / NETCONF / Telnet） | 风险等级完全不同。生成错了是粘贴前能看见，下发错了是业务中断。这是另一个产品，不是这个功能 |
| 自动修改用户的命令 | 用户粘的是现网配置，改了再还给他，责任就模糊了 |
| 多轮长对话记忆 | 每轮独立。上下文越堆越贵，且旧上下文会污染新判断 |
| 自动重试 | 自费用户，重试等于替他烧钱 |
| 网页版 / 手机端 | 已定：只做 exe。也避免了后端、账号、跨端同步三套东西 |
| 用向量库做检索 | `explain.CATALOG` 是 170 条结构化 Doc，按 key / 分组 / 正则检索已经够准，加向量库是给自己找麻烦 |
| 让模型总结现网配置给出"优化建议" | 输出会变得很有说服力且很难验证。网工改现网要的是依据，不是建议 |

## 附录：一次完整调用的数据流

以「给 VLAN 10 20 30 划 8 个 access 口」为例，从点按钮到看见命令：

```
1  ui/ai_page.py    取输入文本、当前厂商（h3c）
2  ai/intent.py     第一轮：29 场景清单 → {"scenario":"vlan_port","confidence":0.86}
3  ai/schema.py     从 registry.get("vlan_port") 导出参数 schema
4  ai/intent.py     第二轮：schema + 原文 → {"params":{...},"missing":[]}
5  ai/intent.py     清洗：key 白名单、值转 str、丢弃多余字段
6  ui/ai_page.py    校验：vendors.supports("h3c","vlan_port") → True
7  ui/ai_page.py    self.store[("h3c","vlan_port")] = 合并后的参数
8  ui/window.py     self._restore_fields()        → 表单控件更新
9  ui/window.py     _scroll_to_card + _flash_card → 滚过去、闪两下
10 ui/window.py     self._generate("vlan_port")   → 左侧脚本区出现命令
```

体检那条链路是独立的，走另一条路：

```
1  ui/window.py     取 audit_in 里的文本
2  audit.py         第一层：安全体检 → Report（风险清单 + 健康分）
3  ai/rules.py      第二层：语法校对 → (findings, unmatched)
4  ui/window.py     渲染三段到 audit_out
5  ai/advise.py     第三层（勾选才跑）：脱敏 → 带上前两层结论 → 模型
6  ui/window.py     后台线程回主线程，重新渲染
```

第 3 步值得单独说：**语法校对可以反过来查自己生成的命令**。
把主页面生成的一批命令粘进体检页，规则层跑一遍——如果哪天模板改错了，
用户自己就能发现，不用等到粘到设备上才发现。这是个免费的回归测试，
只是现在得手动做，没接成自动的。

## 附录 B：落地时跟设计稿的出入

设计稿是开工前写的，实现过程中有几处判断需要修正。都记在这儿，免得下次又踩。

**先看第 7 条**——那条改的是整体结构（查错从独立页变成体检的第三层），
比前六条要紧。前六条是实现细节。

**1. 视图栈的初始值不能一律当成「用户视图」**

这是设计时漏掉的最大一个坑。用户粘过来的通常是 `display current-configuration`
的输出，**里面没有 `system-view`**——配置文件本身已经在系统视图下。
如果按设计从 user 视图起算，所有接口下的 `port link-type` 都会被判成「位置错误」，
一次误报几百条，这个功能直接不可用。

改法：先扫全文，有 `system-view` / `configure terminal` 的才从 user 起算，
没有的从 system 起算。`tools/ai_test.py` 里专门有一条「配置文件片段不误判视图」盯着它。

**2. schema 导出没有塞进 `registry.py`**

设计里写的是「新增 `registry.export_schema()`」。实现时改成放在 `scg/ai/schema.py`，
只读 `registry.SCENARIOS`，不往里加东西。

理由：内核不该知道 AI 的存在。放进去之后，「把 `scg/ai/` 整个删掉主程序照样跑」
这条就不成立了——`registry` 会留下一个没人调用的函数和一个为模型服务的字段命名约定。
现在 `registry.py` 一行没改。

**3. 「高亮被改动的参数控件」做不到，换了个做法**

`ttk.Entry` 不支持直接改背景色，要换主题样式才能变色，代价太大。
改成：卡片外框闪两下 + 自动滚到那个场景 + 结果区列出「哪些值覆盖了原值」。
效果上是一样的——用户能看出改的是哪一块——但实现成本低得多。

**4. 流式只用来显示「在动」，不渲染增量文本**

输出是 JSON，逐字渲染出来是 `{"scenarios": "vlan_po…` 这种东西，没有阅读价值。
所以 `on_chunk` 只累加计数，主线程用它更新一句话状态。
流式真正的价值是**让用户知道请求没死**，不是展示内容。

**5. 顺手补了一个兼容性问题**

有些网关会忽略 `stream: true`，直接返一整段普通 JSON。第一版只处理 SSE 帧，
遇到这种就报 `bad_format`。现在非 `data:` 开头的行会收起来做兜底解析。
同理，部分服务端不认 `response_format`，400 且报文里提到这个字段时去掉重试一次——
这是协议降级，不是自动重试，只发生一次。

**6. 规则数量对不上，但覆盖面更宽**

设计里说「`verify.FIXED` 那 7 条翻译成规则」，实现出来是 5 类规则、9 条具体判据：
7 条陷阱之外，多了「表单级」的厂商错配和端口编号惯例。
`tools/ai_test.py` 里每条判据都有样本，改规则时会立刻知道打没打偏。

**7. 查错不做成独立页签，改成体检的第三层**

这条是 3.1 合入 3.0 主线时改的，也是最大的一处偏离。

原设计给 AI 开了一个「AI 助手」页，上半自然语言、下半粘贴查错。
合入时发现 3.0 已经有「配置体检」页：左边粘贴区、右边报告区、带复制按钮，
功能是安全体检。再放一个粘贴框查语法，用户会不知道该往哪粘——
而且同一个问题可能在两个地方给出两种说法。

改成：AI 助手页只留自然语言填参数；查错拆成体检页的后两层
（离线语法校对 + 在线语义补充），共用同一个粘贴区和报告区。

顺带纠正一个判断：我一开始以为 `rules.py` 跟 `audit.py` 重叠、可以砍掉。
实际看下来两者不重叠——audit 查「安不安全」，rules 查「能不能跑」。
真正的重叠是**界面**，不是规则。所以规则留下，界面合并。

教训：接入一个已有项目之前，先把它的页面和模块清单读完。
这次是先写了 800 行界面，才发现目标项目里已经有七个页签。

**8. 「启用在线功能」这个开关是多余的（3.1.1 删掉）**

3.1.0 发出去当天用户就报了：填了密钥、点保存、测试连接也通过，
主界面仍然显示「纯离线模式」。

原因：`AIConfig` 有个 `enabled` 字段，默认 False，设置弹窗里那个勾选框
默认没勾。而 `ready()` 要求 `enabled and key and base_url and model` 四项全真，
一项假就整条判成离线。**测试连接直接用密钥发请求、不看这个开关**，
于是「测试成功」和「纯离线」同时成立，用户完全没法理解。

这不是忘记勾选的问题，是设计问题：**一个功能如果有「有没有能力」和「开不开」
两个独立状态，就一定会出现两者不一致。** 密钥存在本身就是能力，
「开不开」不该是另一个字段——想停用删密钥就是了。

现在 `ready()` 只看 `key and base_url and model`，`enabled` 字段整个删除，
旧配置文件里那个 `"enabled": false` 被直接忽略，不需要迁移。

**流程上的教训**：这个 bug 51 项自检没抓到，因为自检覆盖的是
「解析、脱敏、规则匹配」，没有覆盖「配置写盘 → 读回来 → 界面判断是否一致」。
以后动 AI 配置相关代码，必须加一条端到端用例：`save()` → `load()` → `ready()`。
